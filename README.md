# Movie Memory

Sign in with Google, tell us your favorite movie, and get fun facts about it, generated by OpenAI
and cached with correctness guarantees.

**Variant chosen: A (Backend-Focused: caching and correctness).** See [Why Variant A](#why-variant-a).

**Stack:** Next.js 16 (App Router), React 19, TypeScript, TailwindCSS 4, Postgres, Prisma 6,
NextAuth (Google OAuth, database sessions), OpenAI API, Vitest.

### Request flow

1. **Auth.** `/` is the landing page and also where Google sign-in returns (`callbackUrl: "/"`).
   If a session exists, it redirects using one rule, `homePathFor(user)`: no favorite movie →
   `/onboarding`, otherwise → `/dashboard`. "First-time user" therefore means "hasn't finished
   onboarding" rather than "account created a moment ago", so a user who signs up and abandons
   onboarding is sent back to it next time.
2. **Protected pages.** `/onboarding` and `/dashboard` call `requireUser()`, which redirects to `/`
   when signed out. Onboarding redirects to the dashboard if a movie already exists, and the
   dashboard redirects to onboarding if it doesn't.
3. **Onboarding.** The form posts to a Server Action that re-checks the session (Server Actions are
   public endpoints), validates with Zod (trim, collapse whitespace, 1–100 chars), and saves with
   `updateMany({ where: { id, favoriteMovie: null } })` so a replayed submission can't overwrite an
   existing choice.
4. **Dashboard.** Server-rendered from the DB (name, email, photo, movie) with fallbacks for a
   missing name (email, then "Movie fan") and a missing photo (initials). The fact card is a small
   client component that calls `GET /api/fact` and renders loading, error and "stale" states.
5. **Facts.** `GET /api/fact` takes **no parameters**. It reads the user id from the session and
   passes it to `factService.getFactForUser(userId)`.

### Data model

| Model                | Why it exists                                                                                       |
| -------------------- | --------------------------------------------------------------------------------------------------- |
| `User`               | NextAuth user + `favoriteMovie String?`. `NULL` = onboarding not done.                              |
| `Account`, `Session` | Required by the NextAuth Prisma adapter. Database sessions mean the cookie is an opaque token and sessions can be revoked server-side. |
| `MovieFact`          | Append-only history of generated facts: `(userId, movie, content, createdAt)`. Index on `(userId, movie, createdAt DESC)` serves the only hot query, "newest fact for this user + movie". |
| `FactGenerationLock` | "Generation in progress" lease. Primary key `(userId, movie)`, plus `token` and `lockedUntil`.       |

Design decisions:

- **Favorite movie is a column on `User`, not a `Movie` table.** There's exactly one favorite per
  user, and titles are free text with no canonical catalog to normalize against ("inception" vs
  "Inception (2010)"). A separate table would add a join without adding integrity.
- **Facts store a snapshot of the `movie` title.** The cache key is `(userId, movie)`, so if a
  user's movie ever changes, facts for the old title are automatically ignored. No invalidation
  code is needed.
- **The cache *is* the facts table.** "Cached fact" = newest `MovieFact` row younger than 60s.
  There's no second store to keep consistent, and history is kept for free.
- **All timestamps are `timestamptz`** so values written by anything other than Prisma (manual
  SQL, defaults) can't be misread across time zones.
- **Cascading deletes** from `User` clean up everything a user owns.

### The fact service (Variant A core)

`lib/facts/fact-service.ts` is a plain function of its dependencies
(`db`, `generateFact`, `now`, `sleep`), with no Next.js imports. That makes it straightforward to
test with a fake clock and a fake OpenAI.

```
getFactForUser(userId)
 ├─ load user.favoriteMovie                     (none → NoFavoriteMovieError → 409)
 ├─ latest = newest fact for (userId, movie)
 ├─ latest younger than 60s?  → return { source: "cache" }
 ├─ try to acquire lease for (userId, movie)
 │   ├─ acquired:
 │   │   ├─ re-read latest; fresh now? → "cache"        (double-checked locking)
 │   │   ├─ call OpenAI
 │   │   │   ├─ ok   → insert fact → "generated"
 │   │   │   └─ fail → have any fact? → "stale" : FactUnavailableError → 503
 │   │   └─ finally: release lease (only if the token is still ours)
 │   └─ not acquired (someone else is generating):
 │       ├─ have an older fact? → return it immediately as "stale"
 │       └─ no fact at all (very first one) → poll ~15s for the other request's result
 │           ├─ fact appears        → "cache"
 │           ├─ lease released, no fact → the other request failed → 503
 │           └─ timeout             → 503 ("still being written")
```

**1. 60-second cache window.** `isFresh = now - createdAt < 60_000`. Exactly 60s is *not* fresh
("less than 60 seconds old"). Tests cover 59.999s (cached) and 60.000s (regenerated).

**2. Burst / idempotency protection: a DB-backed lease (the "generation in progress" flag).**

- *Acquire:* `INSERT` a `FactGenerationLock` row. The composite primary key means only one
  concurrent insert can succeed; the others get a unique violation (`P2002`).
- *Crash recovery:* if the row exists but `lockedUntil` has passed, a request may take it over
  with `UPDATE … WHERE lockedUntil < now`. Postgres re-evaluates the `WHERE` after taking the row
  lock, so when several requests race for an expired lease, exactly one update matches.
- *Release:* `DELETE … WHERE token = mine`, so a slow holder whose lease expired can never delete
  a lease someone else now holds.
- *Double-check after acquiring:* closes the window where request B reads "stale", request A
  generates and releases, then B acquires. Without the re-read, B would generate a second fact.
- *Lease length (30s) > worst-case OpenAI call* (8s timeout × 2 attempts), so a live holder never
  loses its lease.

Why this approach over the alternatives:

| Option                                | Why not (here)                                                                  |
| ------------------------------------- | ------------------------------------------------------------------------------- |
| In-memory lock                        | Breaks with >1 server instance or serverless; the DB lease works across instances. |
| Transaction / advisory lock held across the OpenAI call | Holds a pooled connection and an open transaction for seconds per request; Prisma's interactive transactions have short default timeouts; session-level advisory locks are unsafe with a connection pool. |
| Unique constraint per 60s bucket      | Fixed buckets don't match a sliding "less than 60s old" window (facts at 0:59 and 1:00 land in different buckets). |

**3. Failure handling.** The OpenAI client has an 8s timeout and one retry. On any failure
(timeout, 5xx, empty response, missing key) the service logs the error server-side and returns
the most recent fact with `source: "stale"`. With no fact to fall back on, the API returns a
`503` with a friendly message. Internal error details never reach the client. The lease is always
released in `finally`, so the next request can retry immediately.

**4. Authorization.** Every query is filtered by `userId`, and that id only ever comes from the
server-side session. `/api/fact` accepts no ids, so there is nothing to tamper with. Responses
don't include internal ids. Tests prove a user never gets another user's fact even when both
share the same movie and the other user's fact is fresh.

### Security notes

- Secrets (`OPENAI_API_KEY`, `GOOGLE_CLIENT_SECRET`, `NEXTAUTH_SECRET`) are read only in
  `server-only` modules, so importing them from client code is a build error.
- Database sessions with `httpOnly` cookies are managed by NextAuth.
- The movie title is user input sent to an LLM. It's JSON-encoded in the user message and the
  system prompt says to treat it as data. Output is rendered as text, so React escapes it.
- `/api/fact` responses are `Cache-Control: private, no-store`.

### Testing

28 tests in `tests/`, run against a **real Postgres** test database. The concurrency guarantees
depend on real Postgres behavior (unique violations, row-lock re-checks), so mocking the DB would
test nothing.

- `fact-service.test.ts`: cache window (fresh, 59.999s, exactly 60s, per-movie); concurrency
  (5 simultaneous first requests → 1 OpenAI call and 1 row; a burst during regeneration serves the
  stale fact; expired-lease takeover; "busy" timeout); OpenAI failure (stale fallback, no-cache
  error, lease released after failure, waiters told when the holder fails); authorization (never
  another user's fact; no movie → error).
- `api-fact-route.test.ts`: the real route handler + service + DB, with only the session and
  OpenAI mocked: 401 when signed out, users only see their own facts, 409, stale fallback, and a
  friendly 503 that doesn't leak internals.
- `onboarding-action.test.ts`: server-side validation, saves only for the session user, never
  overwrites, redirects when signed out.
- `validation.test.ts`: trimming, whitespace collapsing, length bounds, non-string input.

I also checked that the suite actually catches regressions by breaking the code on purpose:
changing `<` to `<=` in the cache window, removing the lock, and dropping the `userId` filter
each make the relevant tests fail.

## Why Variant A

The interesting problems in this app are on the backend: deciding when a fact is "fresh",
making sure a refresh-spamming user or five open tabs produce one OpenAI call (not five), and
degrading gracefully when a third-party API is slow or down. These are correctness problems
that can be tested deterministically with a fake clock and a real database. Variant A rewards
exactly that kind of reasoning about data modeling, concurrency and failure modes.

## Key tradeoffs

- **DB lease vs. simpler locks.** Slightly more code than an in-memory mutex, but correct across
  multiple server instances and self-healing after crashes. Cost: a few extra small queries on a
  cache miss (not on a cache hit).
- **Waiters get the stale fact immediately** rather than waiting for the new one. Faster UX for
  bursts. The new fact shows up on the next request. Only the very first fact (nothing to show)
  makes waiters poll.
- **Polling vs. notifications for waiters.** Polling every 500ms is simple and stateless.
  `LISTEN/NOTIFY` would be faster but needs a dedicated connection.
- **App clock as the single source of time.** Cache freshness and lease expiry both use the
  server's clock (injectable for tests), and `createdAt` is written from the same clock.
  Across multiple instances this assumes reasonably synced clocks (NTP); a few hundred ms of skew
  only shifts the 60s window slightly.
- **Keep every fact** (append-only) instead of overwriting one cached row. Simpler invariants
  and a free history, at the cost of unbounded growth (see improvements).
- **Database sessions vs. JWT.** One extra query per request, but sessions are revocable and
  the cookie contains nothing sensitive.
- **Fact fetched client-side** via `/api/fact` rather than in the dashboard's server render, so
  the profile appears immediately and a slow OpenAI call only delays the fact card.
- **Cache Components disabled.** Next 16 scaffolds with it on, but every page here is per-user
  and dynamic, so there's nothing to prerender. The classic model is simpler to reason about.

## What I'd improve with 2 more hours

- **Edit favorite movie** from the dashboard (the data model already handles it: facts are keyed
  by title, so changing the movie naturally invalidates the cache).
- **Retention:** prune old `MovieFact` rows (e.g. keep the last N per user) and add a periodic
  cleanup of expired lock rows (they're harmless but accumulate if processes crash).
- **Rate limiting** per user on cache misses, to cap OpenAI spend even across different movies.
- **Avoid repeat facts** by passing the last few facts to the prompt ("don't repeat these").
- **Structured logging/metrics** for cache hit rate, OpenAI latency and fallback rate.
- **End-to-end tests** (Playwright) of the full sign-in → onboarding → dashboard flow with a
  mocked OAuth provider.
